Three bugs found — fix all three before rerunning
🔴 Bug 1 — CRITICAL: Augmentation on ImageNet-normalized floats (Data corruption + potential NaN deadlock)
What's happening: Your preprocess_fundus() returns a float32 array in ImageNet-normalized range (roughly −2.1 to +2.7). That value is stored in the cache. Then __getitem__ passes it directly to albumentations transforms like CLAHE, ColorJitter, and RandomBrightnessContrast.

Albumentations expects either uint8 [0–255] or float32 [0.0–1.0]. Passing normalized floats causes CLAHE to receive all-zero/negative inputs, ColorJitter to produce garbage values, and ElasticTransform to produce NaN outputs in some albumentations versions. This means every single training image is corrupted data entering your model. This explains NaN losses → the NaN skip continues the loop → CPU stuck spinning.
# WRONG — preprocess_fundus normalizes first, then augmentations run on normalized data self.cache[i] = preprocess_fundus(img, size=CFG['image_size']) # returns float32 in [-2.1, 2.7] # ... later in __getitem__: img = self.transform(image=img)['image'] # CLAHE/ColorJitter see -2.1 to +2.7 → garbage
✓ FIX — Cache raw uint8, normalize AFTER augmentation
In APTOSDataset.__init__, cache the image WITHOUT normalization:

# Store uint8 after preprocessing but BEFORE normalization def preprocess_fundus_no_norm(img, size): img = cv2.resize(img, (512, 512)) img = ben_graham(img) img = green_channel_clahe(img) img = crop_circle(img) img = cv2.resize(img, (size, size)) return img # uint8 [0-255] — correct for albumentations # In pre-caching: self.cache[i] = preprocess_fundus_no_norm(img, size=CFG['image_size']) # In __getitem__, augment THEN normalize: if self.transform: augmented = self.transform(image=img)['image'] # augment uint8 # Normalize after augmentation (ToTensorV2 converts to tensor) # Add Normalize to the END of your augmentation pipeline: # A.Normalize(mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]) # ToTensorV2()
Also add A.Normalize(mean=[0.485,0.456,0.406], std=[0.229,0.224,0.225]) just before ToTensorV2() in both get_train_aug() and get_val_aug().
🔴 Bug 2 — SLOWLOCK: ElasticTransform + GridDistortion at 512px with num_workers=0 (CPU bottleneck)
What's happening: num_workers=0 means ALL augmentation runs in the main process, blocking the training loop. At 512px, ElasticTransform and GridDistortion scale quadratically with resolution — they're 5× slower at 512px than 224px. Each batch of 18 images takes 3–6 seconds of pure CPU time just for augmentation. At 163 batches per epoch, that's 8–16 minutes per epoch × 60 epochs = 8–16 hours total. This is your 12-hour stuck situation — it's not a crash, the kernel is just computing augmentations for hours.
# The slow augmentations at 512px (each takes 50-200ms per image): A.ElasticTransform(alpha=120, sigma=6, p=0.2), # O(n²) — very slow at 512px A.GridDistortion(num_steps=5, distort_limit=0.3), # O(n²) — very slow at 512px A.OpticalDistortion(distort_limit=0.05, ...), # Also slow # With num_workers=0 and 18 images per batch: 18 × 150ms = 2.7s per batch
✓ FIX — Remove the 3 slow augmentations AND enable num_workers=2
# REMOVE from get_train_aug(): # A.GridDistortion(...) ← delete # A.OpticalDistortion(...) ← delete # A.ElasticTransform(...) ← delete # A.Downscale(...) ← delete (causes resolution inconsistency) # These are sufficient for SOTA fundus augmentation: # Flips, rotate, shift-scale-rotate, color jitter, CoarseDropout # In CFG, change: 'num_workers': 2, # Workers only do augmentation (images are cached in RAM) # Each worker gets a COPY of cache — fine since images are small # In create_dataloaders(), change: nw = CFG.get('num_workers', 2) # Always use workers regardless of precache pw = True # persistent_workers pf = 2 # prefetch_factor
Why workers are safe here: Pre-cached images are read-only numpy arrays. Each worker forks and gets its own copy. With 3,662 cached uint8 images at 512px: 3,662 × 512 × 512 × 3 = ~2.9 GB × 2 workers = ~6 GB extra RAM. Kaggle has 30 GB — completely safe.
🟡 Bug 3 — MINOR: use_vessel attribute not propagating through DataParallel
What's happening: base.use_vessel = False sets the attribute on the unwrapped model. But when DataParallel runs the forward pass, it creates replicas internally. The self.use_vessel attribute on replicas may not be updated. This means the vessel decoder might run when it shouldn't (or vice versa), causing a shape mismatch crash that PyTorch catches as a NCCL timeout — manifesting as a hang.
